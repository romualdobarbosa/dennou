## O que faz
`git rebase` pega os commits do branch atual que não estão na base e os **reaplica um a um** em cima de outro ponto. O resultado é um histórico linear, como se o trabalho tivesse começado a partir da ponta mais recente da base. Como cada commit é recriado, todos ganham hashes novos.

## Uso
```bash
git switch feature
git rebase main               # reaplica os commits de feature em cima de main
git rebase -i HEAD~4          # rebase interativo dos últimos 4 commits
```

## Flags úteis
- `-i` / `--interactive` — abre um editor com a lista de commits para reordenar, juntar, editar ou remover.
- `--continue` — continua depois de resolver um conflito e fazer `git add`.
- `--skip` — descarta o commit que está em conflito e segue.
- `--abort` — cancela tudo e volta ao estado de antes do rebase.
- `-x <comando>` — roda um comando (por exemplo, os testes) depois de reaplicar cada commit e para se ele falhar.

## Exemplo
### Atualizar um branch de feature
```bash
git fetch origin
git switch feature/login
git rebase origin/main
# se houver conflito: edite, git add <arquivo>, git rebase --continue
git push --force-with-lease
```

Comparado ao `git merge main`, o rebase evita commits de merge "atualizando com main" e deixa o histórico linear. O custo é reescrever os commits, o que exige push forçado se o branch já foi publicado.

### Rebase interativo
```bash
git rebase -i HEAD~4
```
Abre algo como:
```
pick a1b2c3d adiciona modelo de usuário
pick d4e5f6a corrige typo
pick 0718293 adiciona endpoint de login
pick 9a8b7c6 ajusta testes
```

Trocando a palavra no início de cada linha:
- `pick` — mantém o commit.
- `reword` (`r`) — mantém, mas permite editar a mensagem.
- `edit` (`e`) — para nesse commit para você alterá-lo (`git commit --amend`) antes de continuar.
- `squash` (`s`) — junta com o commit anterior e combina as mensagens.
- `fixup` (`f`) — junta com o anterior descartando a mensagem deste.
- `drop` (`d`) — remove o commit.

Reordenar as linhas reordena os commits.

### Conflitos durante o rebase
Os conflitos aparecem commit a commit. Um detalhe que confunde: durante o rebase, `--ours` se refere à base (o branch em que você está reaplicando) e `--theirs` ao commit que está sendo reaplicado, o inverso do que acontece num merge.

### A regra de ouro
Não faça rebase de commits que outras pessoas já baixaram e usam como base. Reescrever um histórico compartilhado obriga todos a reconciliar seus branches. Em branches pessoais ou antes de abrir um pull request, o rebase é seguro. Para manter o hábito no `git pull`, use `git pull --rebase` ou configure `git config pull.rebase true`.

Se algo der muito errado depois de terminar o rebase, o estado anterior pode ser recuperado pelo `git reflog`, procurando a entrada anterior ao início do rebase e fazendo `git reset --hard` para ela.

### Commits de correção com --fixup e --autosquash
Quando você percebe um erro num commit antigo do seu branch, não precisa abrir o rebase interativo e mover linhas à mão. Faça a correção e crie um commit marcado como conserto daquele commit específico:

```bash
git add models.py
git commit --fixup=a1b2c3d       # cria "fixup! adiciona modelo de usuário"
git rebase -i --autosquash main
```

Com `--autosquash`, o Git já posiciona o commit `fixup!` logo abaixo do alvo e marca como `fixup` na lista; basta salvar. Também existe `git commit --squash=<sha>`, que gera um `squash!` e preserva a mensagem para edição. Para não precisar lembrar da flag, ative `git config --global rebase.autoSquash true`.

### Mudando a base com --onto
`git rebase --onto nova-base base-antiga branch` pega só os commits entre `base-antiga` e `branch` e os reaplica sobre `nova-base`. Caso típico: você criou `feature-b` a partir de `feature-a`, e agora quer que `feature-b` saia direto de `main`, sem os commits de `feature-a`:

```bash
git rebase --onto main feature-a feature-b
```
