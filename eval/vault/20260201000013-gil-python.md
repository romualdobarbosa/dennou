## Definição
O GIL (Global Interpreter Lock) é uma trava (mutex) global do CPython, a implementação de referência do Python. Ele garante que apenas uma thread execute bytecode Python por vez dentro de um mesmo processo. Na prática, threads Python não executam código Python puro em paralelo em vários núcleos, mesmo que a máquina tenha muitos.

## Como funciona
O CPython gerencia memória por contagem de referências: cada objeto tem um contador que sobe e desce o tempo todo. Se várias threads alterassem esses contadores ao mesmo tempo sem proteção, o resultado seria corrupção de memória. Em vez de colocar uma trava em cada objeto, o que deixaria o código single-thread mais lento, o CPython optou por uma trava única. Isso também simplificou a vida de quem escreve extensões em C, que podem assumir que estão sozinhas enquanto seguram o GIL.

Uma thread precisa segurar o GIL para rodar bytecode. O interpretador força a troca periodicamente: desde o Python 3.2, uma thread que está esperando pede a liberação depois de um intervalo configurável, que por padrão é de 5 milissegundos.

```python
import sys
sys.getswitchinterval()   # 0.005
```

### Quando o GIL atrapalha e quando não
O ponto central é separar trabalho limitado por CPU de trabalho limitado por I/O.

- **I/O-bound** (rede, disco, banco de dados, `time.sleep`): a thread libera o GIL enquanto espera a operação de I/O. Outras threads rodam nesse meio-tempo. Por isso `threading` e `concurrent.futures.ThreadPoolExecutor` funcionam bem para baixar muitas URLs ou fazer várias consultas ao mesmo tempo.
- **CPU-bound** (cálculo numérico em Python puro, laços pesados, parsing): as threads disputam o GIL e, no total, o programa não fica mais rápido. Às vezes fica até mais lento por causa do custo de troca.

```python
from concurrent.futures import ProcessPoolExecutor

def pesado(n):
    return sum(i * i for i in range(n))

with ProcessPoolExecutor() as ex:
    resultados = list(ex.map(pesado, [10**7] * 4))
```

### Formas de contornar
- **multiprocessing / ProcessPoolExecutor**: cada processo tem seu próprio interpretador e seu próprio GIL. O custo é a serialização (pickle) dos dados trocados entre processos e o uso maior de memória.
- **Extensões em C que liberam o GIL**: NumPy, por exemplo, libera o GIL em muitas operações vetorizadas, então threads com NumPy podem ganhar paralelismo real.
- **asyncio**: não dá paralelismo de CPU, mas é eficiente para muitas operações de I/O concorrentes em uma única thread.
- **Outras implementações**: Jython e IronPython não têm GIL; o PyPy tem.

O GIL não torna o seu código thread-safe. Operações como `contador += 1` são várias instruções de bytecode, e a troca de thread pode acontecer no meio delas. Para estado compartilhado, use `threading.Lock` ou estruturas como `queue.Queue`.

### Subinterpretadores
O Python 3.12 (PEP 684) passou a permitir que cada subinterpretador tenha seu próprio GIL. Isso abre caminho para paralelismo dentro de um mesmo processo, embora o uso direto dessa API ainda seja voltado a quem escreve extensões e ferramentas.

### O Python sem GIL (free-threaded)
A PEP 703 propôs tornar o GIL opcional. O Python 3.13 trouxe um build experimental chamado **free-threaded**, distribuído separadamente; o executável costuma se chamar `python3.13t`. Nesse build, threads executam bytecode em paralelo de verdade. No 3.14, a PEP 779 tirou o build free-threaded do status experimental, mas ele continua opcional: o build padrão ainda tem GIL.

Para descobrir em tempo de execução se o GIL está ativo, use a função `sys._is_gil_enabled()`, disponível a partir do Python 3.13. Para saber se o interpretador foi compilado com suporte a free-threading, consulte `sysconfig.get_config_var("Py_GIL_DISABLED")`, que retorna 1 nesse caso. Mesmo no build free-threaded, o GIL pode ser reativado em tempo de execução, por exemplo quando é importada uma extensão em C que não declara suporte; dá pra forçar o comportamento com a variável de ambiente `PYTHON_GIL=0` ou com a opção `-X gil=0`.

```python
import sys
print(sys._is_gil_enabled())   # False no build free-threaded sem GIL
```

## Analogia
É uma cozinha com um único fogão e várias pessoas cozinhando. Enquanto alguém espera a massa descansar (I/O), outra pessoa usa o fogão. Mas se todo mundo precisa do fogão o tempo todo (CPU), contratar mais cozinheiros não acelera nada: é preciso mais fogões, ou seja, mais processos.
