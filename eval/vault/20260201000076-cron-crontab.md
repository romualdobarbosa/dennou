## O que é
O cron é o agendador de tarefas clássico do Unix. Cada usuário tem uma tabela (crontab) com linhas que dizem **quando** e **o quê** executar. O daemon do cron verifica a tabela a cada minuto e roda os comandos cujo horário bateu.

## Sintaxe
```bash
crontab -e      # edita a crontab do usuário atual
crontab -l      # lista
crontab -r      # APAGA a crontab inteira, sem confirmação
sudo crontab -u ana -l   # crontab de outro usuário
```

Cada linha tem cinco campos de tempo seguidos do comando:

```text
┌───────── minuto (0-59)
│ ┌─────── hora (0-23)
│ │ ┌───── dia do mês (1-31)
│ │ │ ┌─── mês (1-12 ou jan-dec)
│ │ │ │ ┌─ dia da semana (0-7, 0 e 7 = domingo, ou sun-sat)
│ │ │ │ │
* * * * * comando
```

Operadores em cada campo:
- `*` — qualquer valor.
- `,` — lista: `1,15` (dias 1 e 15).
- `-` — intervalo: `1-5` (segunda a sexta).
- `/` — passo: `*/10` no campo de minuto significa a cada 10 minutos.

Atalhos: `@reboot` (uma vez, ao iniciar), `@hourly`, `@daily`, `@weekly`, `@monthly`, `@yearly`.

## Exemplo
```text
# todo dia às 3h da manhã
0 3 * * * /home/usuario/bin/backup.sh

# a cada 15 minutos, em dias úteis, das 8h às 18h
*/15 8-18 * * 1-5 /usr/local/bin/coleta.sh

# às 0h30 do primeiro dia de cada mês
30 0 1 * * /opt/relatorio/gerar.sh

# ao ligar a máquina
@reboot /home/usuario/bin/montar-cache.sh
```

Uma regra que surpreende: quando **dia do mês** e **dia da semana** estão os dois restritos (nenhum é `*`), o comando roda se **qualquer um** dos dois bater, e não os dois. `0 9 13 * 5` roda todo dia 13 **e** toda sexta-feira, e não só nas sextas-feiras 13.

Além das crontabs de usuário, existem `/etc/crontab` e os arquivos em `/etc/cron.d/`, que têm um **sexto campo** com o usuário que executa o comando, e as pastas `/etc/cron.daily/`, `/etc/cron.hourly/` etc., em que scripts executáveis são rodados na frequência indicada.

Para conferir uma expressão, sites como crontab.guru traduzem a linha para linguagem natural. Em sistemas com systemd, os **timers** do systemd são uma alternativa que integra logs no journal e permite execuções perdidas com `Persistent=true`.

## Gotchas
### Funciona no terminal, mas não no cron
A causa mais comum é o **ambiente**. O cron roda os comandos com um ambiente mínimo: não lê seu `.bashrc` nem `.profile`, usa `/bin/sh` como shell e um `PATH` reduzido, tipicamente só `/usr/bin:/bin`. Comandos em `/usr/local/bin`, `~/.local/bin` ou num ambiente virtual Python não são encontrados. Soluções:
- Use caminhos absolutos para tudo: `/home/usuario/projeto/.venv/bin/python /home/usuario/projeto/job.py`.
- Ou defina variáveis no topo da crontab, que valem para as linhas abaixo:

```text
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""
```

O diretório de trabalho é o home do usuário, então caminhos relativos no script também falham; faça `cd` para o diretório certo dentro do comando.

### Guardar a saída
Por padrão, a saída do comando é enviada por e-mail local para o usuário (ou para o endereço em `MAILTO`); sem servidor de e-mail configurado, ela se perde. Redirecione para um log:

```text
0 3 * * * /home/usuario/bin/backup.sh >> /home/usuario/logs/backup.log 2>&1
```

### O sinal de porcentagem
Na crontab, o caractere `%` é especial: o primeiro `%` não escapado vira o fim do comando, e todo o texto depois dele é enviado como **entrada padrão** do comando, com os `%` seguintes convertidos em quebras de linha. Isso quebra comandos com `date`:

```text
# ERRADO: o comando vira só "tar -czf /backups/site-$(date +"
0 2 * * * tar -czf /backups/site-$(date +%F).tar.gz /var/www

# CERTO: escape com barra invertida
0 2 * * * tar -czf /backups/site-$(date +\%F).tar.gz /var/www
```

Outra saída é mover o comando para um script e chamar o script na crontab, onde `%` não tem significado especial.
