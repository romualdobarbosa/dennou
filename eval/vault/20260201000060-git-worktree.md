## O que faz
Cria diretórios de trabalho adicionais ligados ao **mesmo repositório**. Cada worktree tem um branch diferente em checkout, mas todos compartilham o mesmo `.git` (objetos, branches, configuração). Assim dá para corrigir um bug urgente em `main` sem mexer no trabalho pela metade do seu branch de feature, e sem precisar de `git stash` ou de clonar o repositório de novo.

## Uso
```bash
git worktree add ../projeto-hotfix main          # novo diretório com main
git worktree add -b fix/login ../projeto-login   # cria o branch e o diretório
git worktree list                                # lista os worktrees
git worktree remove ../projeto-hotfix            # remove um worktree
git worktree prune                               # limpa registros de pastas apagadas à mão
```

## Flags úteis
- `-b <branch>` — cria um branch novo a partir do commit indicado (ou do HEAD) para o worktree.
- `--detach` — cria o worktree em detached HEAD, útil para inspecionar um commit ou tag.
- `--force` — permite operações normalmente bloqueadas, como remover um worktree com alterações não commitadas.
- `lock` / `unlock` — impede que um worktree em disco removível seja limpo pelo `prune`.

## Exemplo
```bash
# estou no meio de uma feature e chega um bug urgente
git worktree add ../app-hotfix main
cd ../app-hotfix
git switch -c hotfix/timeout
# corrige, testa, commita, faz push
cd ../app
git worktree remove ../app-hotfix
```

Regras e cuidados:
- O mesmo branch não pode estar em checkout em dois worktrees ao mesmo tempo; o Git recusa para evitar que um diretório fique com arquivos desatualizados em relação ao branch.
- Commits feitos em qualquer worktree aparecem imediatamente para os outros, porque o banco de objetos é um só.
- Arquivos ignorados, como ambientes virtuais e `node_modules`, não são compartilhados: cada worktree precisa da própria instalação de dependências.
- Apagar a pasta com `rm -rf` deixa um registro órfão; rode `git worktree prune` depois, ou use sempre `git worktree remove`.
