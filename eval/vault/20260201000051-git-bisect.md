## O que faz
Encontra o commit que introduziu um bug fazendo **busca binária** no histórico. Você informa um commit em que o bug existe (bad) e um em que não existe (good); o Git faz checkout do commit do meio, você testa e diz se está bom ou ruim, e o processo se repete. Com 1000 commits no intervalo, bastam cerca de 10 passos.

## Uso
```bash
git bisect start
git bisect bad                  # o commit atual tem o bug
git bisect good v2.3.0          # essa versão funcionava
# o Git faz checkout de um commit intermediário; teste e responda:
git bisect good    # ou
git bisect bad
# ... repete até aparecer "<sha> is the first bad commit"
git bisect reset                # volta para onde você estava
```

## Flags úteis
- `git bisect skip` — pula um commit que não dá para testar (não compila, por exemplo).
- `git bisect run <comando>` — automatiza: o Git roda o comando em cada passo e usa o código de saída. 0 significa good; de 1 a 127 (exceto 125) significa bad; 125 significa skip.
- `git bisect log` — mostra os passos dados; `git bisect replay` refaz a partir de um log.
- `git bisect start <bad> <good>` — informa os dois extremos já no início.
- `git bisect terms --term-old ok --term-new quebrado` — troca as palavras quando "good/bad" não faz sentido, por exemplo para achar quando algo ficou **mais rápido**.

## Exemplo
```bash
git bisect start HEAD v2.3.0
git bisect run pytest tests/test_frete.py -x -q
# ...
# 7d1e2f3 is the first bad commit
git show 7d1e2f3
git bisect reset
```

Dicas:
- Quanto mais focado e rápido o teste, melhor: um script que reproduz só o bug costuma ser mais confiável que a suíte inteira.
- Durante o bisect você está em detached HEAD; não faça commits ali.
- Commits pequenos e que compilam individualmente tornam o bisect muito mais útil, porque o commit apontado mostra exatamente a mudança culpada.
