## Definição
`git fetch` **baixa** os commits e referências do remoto e atualiza os branches de rastreamento (`origin/main` etc.), sem tocar nos seus branches locais nem nos seus arquivos. `git pull` faz o `fetch` **e em seguida integra** o branch remoto no branch atual, por merge (padrão) ou por rebase.

## Como funciona
```bash
git fetch origin                 # só atualiza origin/*
git log main..origin/main        # o que chegou de novo
git diff main origin/main        # o que mudaria
git merge origin/main            # integra quando quiser

git pull                         # = fetch + merge
git pull --rebase                # = fetch + rebase
git pull --ff-only               # só integra se for fast-forward
```

Por que preferir `fetch` em muitas situações:
- Dá para **olhar antes de integrar**. O `pull` integra na hora e pode gerar conflitos ou um merge commit inesperado.
- É sempre seguro: nunca altera trabalho local.
- `git fetch --prune` remove referências de branches que foram apagados no remoto.

Configurações úteis do `pull`:

```bash
git config --global pull.rebase true    # pull sempre com rebase
git config --global pull.ff only        # pull só aceita fast-forward
```

Em versões recentes do Git, quando o branch local e o remoto divergiram e nenhuma dessas opções está configurada, o `pull` para com a mensagem "Need to specify how to reconcile divergent branches", pedindo para você escolher entre merge, rebase ou fast-forward only.

O `origin/main` local é uma "foto" do remoto no momento do último fetch. Se você não fizer fetch, ele não muda, mesmo que o servidor tenha commits novos. É por isso que `git status` pode dizer "Your branch is up to date with 'origin/main'" e mesmo assim o push ser rejeitado: a comparação é com a foto antiga.

## Analogia
`fetch` é baixar a correspondência e deixar na mesa; `pull` é baixar e já abrir e arquivar tudo nas suas pastas.
